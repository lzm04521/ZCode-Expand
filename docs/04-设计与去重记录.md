# 设计与去重记录

## Dedupe Ticket

**Intent signature**：在 ZCode 安装包（Electron + asar）内维护跨版本的代码补丁；提供按版本记录的补丁集、可离线运行的应用/校验/回滚工具链；把自定义功能代码外置到本仓库源码而非直接写在压缩产物里。

**Queries**

- 本仓库 / 本机是否已有同类 asar 补丁工具或脚本
- 全局 npm 是否已有 `@electron/asar` 可用（`npm ls -g --depth=0`、npx 缓存）
- ZCode 是否已提供官方扩展面能覆盖需求（`~/.zcode` 下的 skills / agents / commands / plugins / hooks / mcp）
- `resources/` 下是否有 asar 外的可配置文件

**Top matches**

- 无同类实现。`D:\GitHub` 下无 asar 相关仓库；全局 npm 只有 `npm` / `nrm` / `webpack-cli`，无 `@electron/asar`，npx 缓存也没有
- 官方扩展面已覆盖"加能力"类需求（skills / agents / commands / plugins / hooks / mcp），但**无法修改内置 UI 与内置行为**，这正是本项目存在的原因
- `resources/model-providers/models_catalog_*.json`、`resources/config/default.json`、`resources/glm/packages/*` 属于 asar 外的可直接改面，不需要重打包

**Decision**：自建零依赖工具链（`scripts/lib/asar.mjs` 等），不引入 `@electron/asar`。

**Rationale**

- `@electron/asar` 只解决"打包/解包"，不解决本项目真正的问题——**跨版本的锚点记录、匹配次数断言、幂等应用、产物自检**。这层必须自己写
- 离线可用、可审计。补丁工具要动的是 300MB 的系统安装文件，链路越透明越好
- asar 格式本身足够简单（无压缩，索引是明文 JSON），自研读写是可控的，代价是正确性由本仓库负责——因此把自检做得比较重（逐字节比对 + integrity 核对 + 语法门禁）

**未采用**：`OnlyLoadAppFromAsar = 0` 允许 `resources/app/` 目录形态加载，理论上可让补丁变成纯文件拷贝。但 `app.asar` 与 `app/` 同时存在时的优先级**没有实测**，贸然改加载形态有让应用起不来的风险，性价比不划算，暂不做。

## 关键设计决策

1. **补丁集按版本分目录**，而不是一个补丁描述所有版本。理由是锚点和文件名都会随版本变，用条件分支挤在一个文件里会让"这条补丁到底适不适配当前版本"变得不可读。
2. **锚点包含后继字符**，换取天然幂等。重复 apply 不会重复插入。
3. **功能代码外置**。包内只留一行调用 `window.__ZC_EXPAND__`。包内补丁面越小，跨版本适配成本越低。
4. **失败即中止，不做降级**。锚点匹配次数不符、语法不通过、自检不通过，一律报错退出，不写安装目录。宁可让用户手工处理，也不要出现"改了一半"的状态。
5. **`integrity` 重算**。虽然当前 fuse 关闭不做校验，仍然让产物自洽，避免官方将来开启校验时突然失效。

## 开发与评审过程中修掉的真实缺陷（留档，避免重犯）

这些都是"看起来通过、实际错了"的类型，比直接报错危险得多：

1. **路径前导斜杠不一致导致替换被静默跳过**
   补丁集里写 `out/main/xxx.js`，asar 索引里的条目是 `/out/main/xxx.js`。`Map.get()` 拿不到值 → 替换被跳过 → 只有新增文件生效，自检却因为另一处参数没传对而"通过"。
   修法：所有路径经 `canonical()` 归一化；并在 `computeLayout` 加守门——声明了替换却没命中任何条目就直接报错。

2. **自检里的 `return` 静默漏检**
   比对时在 `for...of` 里用 `return` 结束当前叶节点处理，`return` 会跳出**整个目录**的遍历，把同级条目全部跳过，漏检 1736 个文件，而自检报告"通过"。
   修法：先把叶节点收成 Map，再逐个比对，遍历过程不含任何提前返回。

3. **补丁少一个 `}` 导致渲染层语法错误**
   给菜单项插入的 `onSelect` 箭头函数体没闭合，`children:` 落进函数体里。原始文件 `node --check` 是好的，补丁后才坏。
   修法：加语法门禁作为写盘前的硬性条件；补丁片段用脚本按结构拼装并先探针校验，不手数括号。

4. **幂等缺 `marker` 导致重复 apply 直接报错**
   最初只给渲染层与 html 补丁加了 `marker`，6 处 schema 编辑没加。schema 编辑插入内容后锚点即消失，于是重复 apply 时锚点匹配 0 次 → 脚本中止。虽然"锚点包含后继字符"能防止重复插入，但**无法让脚本识别出"已应用"**。
   修法：每处编辑都配一个专属 `marker`（锚点残段 + 插入内容），重复 apply 才算真正的空操作。已在 `patches/3.11.2` 全部补齐。

5. **已完成文件被重复重建**
   补丁已应用时，`buildReplacements` 仍把"内容未变"的文件放进 replace 集合，导致重复 apply 会白重建 300MB。
   修法：产出的文本与原文相同则不放入 replace，配合 marker 让重复 apply 成为纯空操作。

6. **rollback 默认恢复"mtime 最新文件"，而 rollback 自身的留存恰好最新**（2026-09-10 评审发现）
   rollback 覆盖前会把当前 asar 留存为 `pre-rollback-*` 文件，它的 mtime 必然最新；默认按 mtime 挑最新备份时，连续 rollback 第二次会把"回滚前状态"（通常已打补丁）恢复回去——回滚语义反转，且用户正处于"出问题想恢复"的场景。
   修法：默认候选排除 `pre-rollback-` 留存文件（仅 `--from` 可显式恢复）；回滚成功后同步清理 `state/applied-*.json`；留存文件名时间戳从 UTC 改为与 apply 备份一致的本地时间。

## 任务运行状态点（2026-09-11）

**Dedupe Ticket**

**Intent signature**：侧边栏项目行显示"该项目下有正在执行的任务"的状态指示点。

**Queries**

- 渲染层是否已有等价指示（项目行/任务行的运行状态 UI）
- 是否已有"workspace 运行中"的现成判定函数
- 应用 CSS 里是否已有可复用的运行状态点样式

**Top matches**

- 项目行已有**未读小蓝点**（`data-workspace-unread-indicator`，`bg-sky-500`，条件 `!expanded && unread`）——语义是"有未读消息"，不是"正在执行"
- 项目行的流光边框 `$Ct({active:ce})` 的 `ce=te` 是**远程 workspace 连接中**状态，与任务执行无关
- 官方已有运行判定函数 `uwt({workspaceState})`（用于"移除运行中 workspace"确认框）：`draftRuntime.status` 或任一 `taskRuntimeByTaskId[*].status` ∈ {`creating`,`restoring`,`streaming`}（`styles-DyAcaLKy.js` @3267723）

**Decision**：新增运行状态点，判定与 `uwt()` 同源；样式仿未读蓝点（同尺寸同位置），但用 success 绿 + 脉冲动画区分语义，不与未读蓝点混淆。

**Rationale**

- 判定逻辑照抄官方函数，避免自造"什么算运行中"的标准（官方确认框怎么判，我们就怎么判）
- 颜色不用蓝：蓝点已被"未读"占用，同色同位置两个点无法区分；`--color-success` 是应用主题变量，dark 模式自动跟随
- 点的布局类（`h-1.5 w-1.5 shrink-0 rounded-full`）与未读点完全一致（JIT 白名单内必然存在）；颜色动画用自定义 class `zc-xp-running`、由外置模块注入 `<style>`，不赌 `emerald`/`animate-pulse` 是否在 Tailwind JIT 产物里
- 判定入口外置为 `__ZC_EXPAND__.isBusy(workspaceState)`，包内只留一行调用，与备注功能同一模式

**证据链**

- 数据源：`WorkspaceSidebarItem` 组件第一行 hook `T=jo(t=>ko(t,e.workspacePath,e.workspaceIdentity))`（@3269539）即 workspace state（含 `draftRuntime`、`taskRuntimeByTaskId`）；组件内 `E=T.activeTaskId` 直接解构证明 `T` 恒有值
- 渲染点：未读蓝点 JSX `!n&&u?(0,$.jsx)("span",{"data-workspace-unread-indicator":...}):null,z?`（@3277749），运行点插在其后
- 远程 workspace：`ko()` 带 `workspaceIdentity` 取远程事实同步的 state，`uwt()` 同样基于它判定，远程项目同样生效

**验证记录（2026-09-11，安装包副本循环）**

| 步骤 | 结果 |
|---|---|
| `apply --home=<副本>` | styles 6 项编辑（备注 4 + 运行点 2）全部应用；语法门禁通过；自检 27276 未改动文件字节一致 + 6 改动条目 integrity 自洽 |
| 再次 `apply` | 「补丁已全部就位，未做任何改动」空操作 |
| `verify --home=<副本>` | 「补丁已全部应用且锚点一致」，新编辑 #5/#6 显示已应用 |
| `rollback --home=<副本>` | SHA256 回到基线 `14aa5db5…` |

真实安装仍未应用补丁（与备注功能一同等 `npm run apply`）。

**已知限制**

- 运行点无 `title` 提示（与未读点同构，`aria-hidden` 纯视觉装饰）；想知道具体哪个任务在跑需展开项目
- `taskRuntimeByTaskId` 的 status 变化会触发组件重渲染——这是既有订阅（`T` 本来就被整棵订阅，`activeTaskId` 同理），本功能不新增订阅成本
- 折叠进「更多」的项目不渲染侧边栏行，自然也看不到运行点（未读点同样如此）

## 待办与已知风险

- **`nx()` 在侧边栏子树内可用性未运行时验证**。`nx()` 内部会取服务上下文（`Yr()`）与 store。理论上侧边栏与设置页在同一棵 provider 树内，但这一点只有启动应用才能确认。若不可用，症状是侧边栏整块渲染报错——用 `npm run rollback` 一条命令即可恢复。
  替代方案（需要时再上）：不从组件内调用 hook，改由包内把 remark 映射写到全局，外置模块只做展示。
- **`resources/app/` 加载形态**未实测（见上文"未采用"）。
- 点 2（所有供应商模型增加思考选项、默认 max）**已于 2026-09-11 实施**，属纯配置改动：
  - `~/.zcode/v2/config.json`：cc-switch 供应商（id `a4bfd05c-17b7-4396-8b75-f488445fe505`）三个模型（`G.DS[1M]`、`G.DS:deepseek-v4-flash[1M]`、`G.BPRO[1M]`）各补 `"reasoning": {"enabled": true, "variants": ["low","high","max"], "defaultVariant": "max"}`；diff 仅三处新增，备份在 `backups/config.json.bak-20260911-000003`。
  - 内置供应商无需改动：GLM-5.3 系在 config.json 中本就 `defaultVariant: "max"`；`models_catalog_*.json` 全量扫描确认 9 个有 `max` 档的模型（kimi-k3 系 / deepseek-v4 系 / glm-5.3 系）默认已全为 `max`，其余模型只有 `enabled/off` 两档（模型不支持 effort 分级，不硬造）。
  - 逆向依据（`out/host/index.js`）：per-model reasoning zod schema 为 `{enabled, variants, defaultVariant, aliases}.passthrough()`；`openCodeReasoningToModelReasoning` 把 `variants` 转成 `{defaultLevel, levels:{每档:{}}}`，与内置 GLM-5.3 实际工作路径一致；档位名合法性集合 anthropic 协议为 `low/medium/high/xhigh/max`。
  - 剩余运行时验证项（需重启 ZCode 后确认）：模型选择器出现 low/high/max 档位且默认选中 max；`max` 是 GLM 系扩展档，cc-switch 本地代理对 `output_config.effort` 的透传行为需实测——若后端报错，切 `high` 即可。改动的文件在重启前若通过 UI 修改模型设置，可能被主进程内存态整体回写覆盖（重跑本节脚本即可恢复）。
- 若官方在后续版本打开 `EnableEmbeddedAsarIntegrityValidation` fuse，本仓库的补丁会因 integrity 对不上而失效——产物自洽能保证"不是这个原因"，但届时需要重新评估整个链路。
