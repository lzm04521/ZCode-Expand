# 机制说明

## 1. 为什么能改：三个实测结论

改 ZCode 安装包前必须确认它不会因此拒绝启动。实测（3.11.2）：

| 检查项 | 结论 | 依据 |
|---|---|---|
| asar 完整性校验 | **关闭** | `app.asar` 对应 fuse `EnableEmbeddedAsarIntegrityValidation = 0`，启动时不校验 |
| 是否只能从 asar 加载 | **否** | `OnlyLoadAppFromAsar = 0`，允许 `resources/app/` 目录形态 |
| 是否加密/加壳 | **否** | asar 头部可正常解析，索引是明文 JSON |

fuse 读法：在 `ZCode.exe` 中定位哨兵串 `dL7pKGdnNz796PbbjQWNKmHXBZaB9tsX`，其后依次为 `版本(1) / fuse 个数 / 各 fuse 状态(0=关,1=开)`。

另外 `RunAsNode`、`EnableNodeOptionsEnvironmentVariable`、`EnableNodeCliInspectArguments` 都是开启的，所以必要时也可以走 `NODE_OPTIONS` / `--inspect` 注入，而不改包。

代码签名方面：`ZCode.exe` 由智谱华章签名（DigiCert，有效期至 2027-03-20），但 `app.asar` 是独立文件、不在 exe 的签名覆盖范围内，改它不会破坏签名。

## 2. asar 文件格式（本机实测）

```
[0:4]   uint32 = 4                   外层 pickle payload 长度
[4:8]   uint32 = 8 + jsonSize        pickle1 长度
[8:12]  uint32 = 4 + jsonSize        pickle2 长度
[12:16] uint32 = jsonSize            索引 JSON 字节数
[16:]   utf8 JSON 索引（无空白压缩）
之后是数据区，条目的 offset 相对数据区起点
```

条目字段：

- 普通文件：`{ size, offset, integrity }`
- unpacked 文件：`{ size, unpacked: true, integrity }`（字节在 `app.asar.unpacked/` 下）

两个容易踩的点（都是实测出来的，不是推断）：

1. **`offset` 在索引里是字符串**（27281/27281 全部如此），`size` 是数字。Electron 读取时会 `parseInt`，但重建时必须照样写字符串，否则产物与原格式不一致。
2. **每个条目都带 `integrity`**：`{algorithm:'SHA256', hash, blockSize:4194304, blocks:[...]}`。实测确认 `hash` 是**全文** SHA256，`blocks[i]` 是**每 4MB 分块** SHA256（多块文件同样成立）。虽然 fuse 关了不做校验，本仓库仍然对改动条目重算，让产物保持自洽——避免将来官方开启该校验时突然失效。

## 3. 重建策略

`computeLayout()` + `writeRepacked()` 的做法：

- 深拷贝索引，保留全部原条目及其字段
- 数据区按原 `offset` 顺序重排（保持局部性），逐条搬运：未改动文件从原 asar 流式读取后原样写出
- 改动文件用新内容，并重算 `integrity`
- 新增文件插入索引并追加到数据区

因为索引里的 offset 是**相对数据区起点**的，所以"索引长度变化导致数据区整体位移"不需要特殊处理，也不存在自引用导致的循环依赖。

内存：流式写盘（8MB 分块），不把 300MB 产物整块驻留。

## 4. 补丁形态：锚点替换 + 外置代码

补丁只做两件事，都追求"最小且可定位"：

- **锚点替换**：`find` / `replace` / `expect`（期望匹配次数）/ `marker`（已应用标志）
  - 匹配次数不符 → 直接报错中止，绝不"尽力而为"
  - `find` 尽量把后继字符一起包含（例如 `recentProjects:e.array(e.string()).default([]),locale:`），这样补丁天然幂等：应用后锚点不再匹配，重复 apply 不会重复插入
- **外置代码**：真正的功能逻辑放在 `src/`，通过 `addFiles` 注入到 asar（本项目是 `out/renderer/zcode-expand/zc-remarks.js`），并在 `index.html` 的入口脚本**之前**插入 `<script>` 标签，保证先于应用代码就绪

包内补丁只留一行调用：

```js
zcXpLabel=window.__ZC_EXPAND__?window.__ZC_EXPAND__.label(i$(e.label,e.remoteTarget),e.workspacePath,zcXp.settings&&zcXp.settings.projectRemarks):i$(e.label,e.remoteTarget)
```

好处：调整显示格式、改文案、加交互细节都只改 `src/` 里的文件，**不必再回到 4.65MB 的压缩代码里定位**；包内补丁面越小，跨版本适配越省事。

`window.__ZC_EXPAND__` 缺失时全部回退到原行为（显示原名、菜单项点了没反应），所以注入失败是"功能不生效"而不是"界面崩掉"。

## 5. 项目备注补丁的落点

目标：侧边栏项目列表（`workspaceSidebar` → `projectsSection`）每一行。

| 文件 | 改动 | 作用 |
|---|---|---|
| `out/renderer/index.html` | 入口脚本前插入 `<script src="./zcode-expand/zc-remarks.js">` | 注入功能模块 |
| `out/main/chunk-WR3FEWGO.js` | 设置 schema 全量 + 局部各插入 `projectRemarks` | 让设置服务放行并持久化该字段 |
| `out/host/chunk-RWMCBKS2.js` | 同上（host 进程同构副本） | 同上 |
| `out/renderer/assets/src-CdedQslh.js` | 同上（渲染层 schema 副本） | 同上 |
| `out/renderer/assets/styles-DyAcaLKy.js` | 4 处：取设置服务、算显示名、渲染点、菜单项 | 显示与编辑入口 |

渲染层 4 处的具体锚点与语义：

1. `let{intl:w}=K(),` → 追加 `zcXp=nx(),`（`nx()` 是设置服务 hook，返回 `{settings, update, ...}`）
2. `=i$(e.label,e.remoteTarget),U=_wt(e),` → 在其后追加 `zcXpLabel=...`。**刻意不改 `re`**，因为 `re` 还可能有非显示用途，只新增变量去渲染
3. `children:re}),!n&&u?` → 改成 `children:zcXpLabel}),!n&&u?`（渲染点是带 `min-w-0 truncate` 的标签 span）
4. 「更多」菜单在同步项（`Z$`）之后插入一个 `rt` 菜单项「编辑备注」

为什么必须改 schema：设置 schema 是 zod `object`，**没有 `.passthrough()` / `.catchall()`**，zod 默认剥离未知键。所以往 `setting.json` 手塞自定义字段无效——下次任何设置写入都会被剥离，内存里也读不到。必须把字段名加进 schema。已有先例可抄：`lastActiveTaskByWorkspace: record(string, string)` 就是"按工作区路径做映射"。

为什么必须改三份 schema：主进程、host 进程、渲染层各有一份同构副本，任何一份剥掉字段都会让链路断掉。

## 6. 安全门禁

`apply.mjs` 的顺序（任何一步失败都不写安装目录）：

1. 校验安装目录、应用版本、补丁集版本三方一致
2. 检查 ZCode 未运行（判定失败时**报错拒绝**，不当作"未运行"）
3. 生成补丁内容：每个锚点校验匹配次数；已应用的按 `marker` 跳过
4. **语法门禁**：补丁后的每个 JS 通过 `node --check`（同一内容先按 ESM 再按 CJS 试，两种都失败才算不通过）
5. 重建 asar 到临时文件
6. **逐条自检**：重新解析产物，未改动文件逐字节比对；改动条目核对 `size` 与 `integrity`；不得多出/缺少条目
7. 备份原 `app.asar` → 替换 → 记录 `state/applied-<版本>.json`

自检实现上有一条经验值得留档：比对时**先把叶节点收成 Map 再遍历比对**，不要"边递归边提前 `return`"。开发过程中曾用 `for...of` 里 `return` 的写法，`return` 会跳出整个目录、静默漏检 1736 个文件，而自检却报告"通过"。这类静默漏检比直接报错危险得多。
